## 0. Set up the practice database

**Use case:** A campus media desk needs to track equipment quantities and borrowing history. Separate equipment and checkout tables let it record repeated loans without duplicating equipment descriptions.

A **schema** is a namespace for database objects. Qualifying a name, such as `m7_lab.equipment`, identifies exactly which table you mean.

Run this setup block once:

```sql
/* 01 */ CREATE SCHEMA IF NOT EXISTS m7_lab;
/* 02 */
/* 03 */ CREATE TABLE IF NOT EXISTS m7_lab.equipment (
/* 04 */     equipment_id integer PRIMARY KEY,
/* 05 */     item_name text NOT NULL,
/* 06 */     available_units integer NOT NULL CHECK (available_units >= 0)
/* 07 */ );
/* 08 */
/* 09 */ CREATE TABLE IF NOT EXISTS m7_lab.checkout (
/* 10 */     checkout_id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
/* 11 */     equipment_id integer NOT NULL
/* 12 */         REFERENCES m7_lab.equipment(equipment_id),
/* 13 */     borrower_code text NOT NULL,
/* 14 */     checked_out_at timestamptz NOT NULL DEFAULT now(),
/* 15 */     returned_at timestamptz
/* 16 */ );
/* 17 */
/* 18 */ CREATE UNIQUE INDEX IF NOT EXISTS uq_m7_active_borrower_equipment
/* 19 */     ON m7_lab.checkout(equipment_id, borrower_code)
/* 20 */     WHERE returned_at IS NULL;
/* 21 */
/* 22 */ INSERT INTO m7_lab.equipment
/* 23 */     (equipment_id, item_name, available_units)
/* 24 */ VALUES
/* 25 */     (101, 'Camera', 2),
/* 26 */     (102, 'Microphone', 3),
/* 27 */     (103, 'Tripod', 1)
/* 28 */ ON CONFLICT (equipment_id) DO NOTHING;
/* 29 */
/* 30 */ SELECT * FROM m7_lab.equipment ORDER BY equipment_id;
```

**Expected in a fresh lab:**

| equipment_id | item_name | available_units |
| --- | --- | --- |
| 101 | Camera | 2 |
| 102 | Microphone | 3 |
| 103 | Tripod | 1 |

Each equipment row represents an equipment type with a quantity, rather than one individually numbered physical item. Each checkout row records one unit borrowed.

| Definition | What it guarantees |
| --- | --- |
| `PRIMARY KEY` | Each row has a unique, non-null identifier. |
| `NOT NULL` | A required value cannot be omitted. |
| `CHECK (available_units >= 0)` | Negative inventory is rejected. `NOT NULL` separately rejects missing quantities. |
| Foreign key on `equipment_id` | Every checkout refers to an existing equipment row. |
| Identity column | PostgreSQL supplies a checkout ID when you omit it. IDs may have gaps. |
| `DEFAULT now()` | The checkout timestamp defaults to the current transaction's start time. |
| Nullable `returned_at` | `NULL` represents an item that has not yet been returned. |

The **partial unique index** applies only to rows where `returned_at IS NULL`. It prevents the same borrower from having two active checkouts for the same equipment type. Once an item is returned, its historical row no longer blocks a new checkout for that pair.

This index does **not** enforce total equipment capacity across different borrowers. The checkout workflow must coordinate stock and checkout records.

**Check yourself:** Would the foreign key stop a borrower from checking out equipment with zero units available? No. It checks that the equipment exists, not that stock is available or the request is authorized.

## 1. COMMIT and ROLLBACK

**Use case:** An online order creates an order record, adds its items, and reserves inventory. These changes need one transaction so a failure does not leave inventory reserved for an order that was never recorded. A deliberate cancellation before commit should undo the whole operation.

A **transaction** is one logical unit of work. `BEGIN` starts it, `COMMIT` persists it, and `ROLLBACK` discards its uncommitted changes. Without an explicit transaction, a client operating in autocommit mode commits each successful standalone statement.

### How selections and transaction boundaries work

The database executes the SQL that your editor sends. Text visible elsewhere in the editor has no effect unless it is executed. In a selection-aware editor, highlighting a complete statement or script and choosing the selection/run action sends that selection. With no selection, the editor may execute the current statement or the whole script, depending on the action and client. Check what will run before clicking; do not assume all Run commands behave alike.

**A statement, a script, and a transaction are different things.** A semicolon ends a statement. A script can contain several statements. An explicit transaction starts when PostgreSQL executes `BEGIN` and ends when it executes `COMMIT` or a full `ROLLBACK` in that same database session. It does not end merely because you reached the bottom of a code block, changed the selection, or saw a result grid.

Why use `BEGIN`? It tells PostgreSQL to keep the following statements in one unit whose changes remain provisional. An `UPDATE` can succeed and return a row while still awaiting the transaction's final decision. `COMMIT` keeps the transaction's changes; a full `ROLLBACK` discards them. The statements are still executed in order, rather than merged into one SQL statement.

For the exercises, select the complete block containing `BEGIN`, all the intended work, and its ending `COMMIT` or `ROLLBACK`. Any verification query after that ending runs outside the transaction you just finished. A reset before `BEGIN` is outside that explicit transaction too.

In a persistent client connection, you **can** execute `BEGIN`, the work, and `COMMIT` in separate selections, provided they all use the same still-open transaction in the same session. This is how Section 5 deliberately demonstrates locks. Separate browser editor runs may not preserve that session. For Supabase SQL Editor practice, send the complete transaction together rather than depending on separate runs retaining it.

Also, a client can wrap a submitted batch in a transaction or send multiple statements together with implicit transaction behavior. Therefore, do not infer the transaction boundary from the number of clicks or selected lines. Use explicit boundaries for these examples, and read your client's execution settings. See PostgreSQL's [transaction tutorial](https://www.postgresql.org/docs/current/tutorial-transactions.html) and [`BEGIN` reference](https://www.postgresql.org/docs/current/sql-begin.html).

### How selective execution changes results

Read the following cases before trying them. The quantity examples assume a camera reset to `2` and no pre-existing open transaction. Cases involving separate runs assume a persistent connection with autocommit enabled, unless stated otherwise.

| What you execute | What happens | Why it differs from the full exercise |
| --- | --- | --- |
| Only a `SELECT` | Reads the current visible value without performing the skipped update. | The editor does not execute earlier lines just because they appear above your selection. |
| Only the complete camera decrement `UPDATE`, as a standalone request | Changes `2` to `1` and commits automatically. | No explicit transaction was opened to hold the change provisionally. |
| A later standalone `ROLLBACK` after that committed update | Does not restore `2`; PostgreSQL warns that no transaction is in progress. | Rollback cannot reach backward into a completed transaction. |
| Only `COMMIT`, with no active transaction | PostgreSQL warns that no transaction is in progress; no skipped work is performed. | `COMMIT` finishes existing work; it does not execute surrounding SQL. |
| `BEGIN` and the update, omitting the ending | Leaves the update uncommitted if the session remains open. That session sees `1`; an ordinary read in another session still sees committed `2`. | A result row is not proof of commit. The open transaction can also hold locks. |
| Only `SAVEPOINT before_optional_change`, outside an explicit transaction block | PostgreSQL rejects it: savepoints can only be used in transaction blocks. | A savepoint needs an existing transaction to mark. |
| `ROLLBACK TO SAVEPOINT before_optional_change` in a new transaction or after the old transaction ended | Cannot find that savepoint. | A savepoint belongs only to the transaction that created it. |
| Only part of a statement, such as `WHERE equipment_id = 101;` | Usually a syntax error. | A selected fragment is not automatically combined with the unselected `UPDATE`. |
| An `UPDATE` with its `WHERE` clause left out, ending the selected text with a semicolon | Can update every row in the table. | A complete but unintended statement may be valid SQL. Select the entire intended statement. |

The same SQL can also show a different result on a second run because the **starting data changed**. Repeating a committed decrement is a new decrement; running the reset again restores the exercise's starting value. Selection, transaction state, starting data, and which result grid is displayed all affect what you observe.

### A. Undo a successful change

First, reset the camera quantity. These inventory-only exercises illustrate transaction control; they do not create complete checkout records.

```sql
/* 01 */ UPDATE m7_lab.equipment
/* 02 */ SET available_units = 2
/* 03 */ WHERE equipment_id = 101;
```

**Predict:** What quantity will the transaction see? What quantity will remain afterward?

Run this entire block together:

```sql
/* 01 */ BEGIN;
/* 02 */
/* 03 */ UPDATE m7_lab.equipment
/* 04 */ SET available_units = available_units - 1
/* 05 */ WHERE equipment_id = 101;
/* 06 */
/* 07 */ SELECT available_units AS provisional_quantity
/* 08 */ FROM m7_lab.equipment WHERE equipment_id = 101;
/* 09 */
/* 10 */ ROLLBACK;
/* 11 */
/* 12 */ SELECT available_units AS after_rollback
/* 13 */ FROM m7_lab.equipment WHERE equipment_id = 101;
```

**Expected:** `provisional_quantity = 1`; `after_rollback = 2`. Some editors display only the final result grid. The final value should still be `2`.

**Read by line:** Line **01** opens the transaction. Lines **03–05** change the quantity; lines **07–08** read that provisional change. Line **10** cancels the transaction. Lines **12–13** read the stored value after cancellation. Selecting only the final query changes neither inventory nor transaction state.

The update was valid and succeeded. `ROLLBACK` deliberately discarded it. A successful statement does not require you to keep the transaction.

### B. Keep the change

Starting from the `2` left by the previous exercise, run:

```sql
/* 01 */ BEGIN;
/* 02 */
/* 03 */ UPDATE m7_lab.equipment
/* 04 */ SET available_units = available_units - 1
/* 05 */ WHERE equipment_id = 101 AND available_units > 0
/* 06 */ RETURNING equipment_id, available_units;
/* 07 */
/* 08 */ COMMIT;
/* 09 */
/* 10 */ SELECT available_units AS after_commit
/* 11 */ FROM m7_lab.equipment WHERE equipment_id = 101;
```

**Expected:** One updated row, with quantity `1`; `after_commit = 1`.

**Read by line:** Line **01** starts the transaction, lines **03–06** update and report the changed row, and line **08** commits. Lines **10–11** verify the committed value outside that transaction. Running only line **08** does not run lines **03–06** for you. Running only lines **03–06** as a standalone autocommit request may make the change permanent before you intended.

`RETURNING` reports the row changed by the update. If no row satisfies the condition, the statement returns no rows. That is a valid outcome, not an SQL error.

**Modify:** Reset the camera to `2`, replace `COMMIT` with `ROLLBACK`, and run the whole block again. Explain why the final quantity changes. A later `ROLLBACK` cannot undo an already committed transaction.

## 2. SAVEPOINTS

**Use case:** While recording an order, a system tries to apply an optional promotion. It can place a savepoint before that optional step, undo the promotion attempt if necessary, and still finish the valid order. Required order and inventory operations must still succeed together.

A savepoint marks a recovery position **inside** a transaction. Rolling back to it undoes later work while keeping earlier work provisional until the transaction commits.

**Predict:** Will the final microphone quantity be `3`, `2`, or `0`?

```sql
/* 01 */ UPDATE m7_lab.equipment
/* 02 */ SET available_units = 3
/* 03 */ WHERE equipment_id = 102;
/* 04 */
/* 05 */ BEGIN;
/* 06 */
/* 07 */ UPDATE m7_lab.equipment
/* 08 */ SET available_units = 2
/* 09 */ WHERE equipment_id = 102;
/* 10 */
/* 11 */ SAVEPOINT before_optional_change;
/* 12 */
/* 13 */ UPDATE m7_lab.equipment
/* 14 */ SET available_units = 0
/* 15 */ WHERE equipment_id = 102;
/* 16 */
/* 17 */ ROLLBACK TO SAVEPOINT before_optional_change;
/* 18 */ COMMIT;
/* 19 */
/* 20 */ SELECT available_units AS after_savepoint
/* 21 */ FROM m7_lab.equipment WHERE equipment_id = 102;
```

**Expected:** `2`. Trace the quantity as `3 → 2 → 0 → 2`. The savepoint did not commit the first change; the final `COMMIT` did.

**Read by line:** Lines **01–03** reset the microphone before the explicit transaction. Line **05** starts it; lines **07–09** set quantity to `2`; line **11** creates the savepoint. Lines **13–15** set quantity to `0`. Line **17** undoes only work after the savepoint, returning to `2` while keeping the transaction open. Line **18** commits. Lines **20–21** verify the result.

### Why running half the savepoint example fails

If you select lines **07–18** without having executed `BEGIN` in the same active session, you have not established the explicit transaction required by this example. In particular, running lines **07–09** as a standalone autocommit request makes the value `2` permanent. A later standalone run of line **11** fails because it has no transaction block in which to create the savepoint. Client batching can affect how a larger partial selection is treated, so do not depend on an omitted boundary being supplied for you.

Executing only line **17** also cannot recreate the missing savepoint. Even if you start a new transaction first, the earlier savepoint does not exist in it. Once a transaction commits or fully rolls back, its savepoints are gone. A line with the same savepoint name visible elsewhere in the editor is not an active database savepoint.

If you execute lines **05–15** in a persistent connection and stop, the savepoint exists, but the transaction remains open. You can then run line **17** followed by line **18** in that **same connection**. The split execution works because the transaction is still active, not because PostgreSQL remembers your Markdown block. For this guided practice, running the whole block together avoids that dependency.

If an error leaves a persistent connection in a failed transaction, issue a full `ROLLBACK`. Then rerun the reset and the complete example. A correctly established savepoint can support error recovery too, but the savepoint must predate the error and still belong to that active transaction. See the [PostgreSQL savepoint reference](https://www.postgresql.org/docs/current/sql-savepoint.html).

**Modify:** Repeat the reset and transaction, replacing `ROLLBACK TO SAVEPOINT before_optional_change` with `ROLLBACK` and removing the following `COMMIT`. The final quantity should be `3`, because the whole transaction was canceled.

## 3. Let the database reject invalid data

**Use case:** Several applications and scripts may update inventory. A database constraint rejects negative quantities regardless of which ordinary write path made the request, even when an application forgot its own validation.

**Predict:** Does this update store `-1`, silently change it to `0`, or raise an error?

Run this statement **by itself**, outside an explicit transaction:

```sql
/* 01 */ UPDATE m7_lab.equipment
/* 02 */ SET available_units = -1
/* 03 */ WHERE equipment_id = 103;
```

**Expected:** PostgreSQL error `23514`, a check constraint violation. The database rejects the change; it does not repair the value for you.

Now run this separately:

```sql
/* 01 */ SELECT equipment_id, item_name, available_units
/* 02 */ FROM m7_lab.equipment
/* 03 */ WHERE equipment_id = 103;
```

The quantity remains what it was before the invalid update: `1` if you followed the guide in order.

If a statement fails inside an explicit transaction, PostgreSQL leaves that transaction in a failed state. In a persistent connection, issue `ROLLBACK` before continuing, or recover to a savepoint established before the error. Do not assume later statements will continue normally.

**Explain:** Why are both `NOT NULL` and `CHECK (available_units >= 0)` needed? A check rejects `FALSE`, but permits an unknown result caused by `NULL`; `NOT NULL` closes that gap.

## 4. Reserve stock and record a checkout together

**Use case:** Two students try to borrow the last tripod. The successful request should both reduce stock and record its checkout; the other should receive an unavailable result. Neither request should create a checkout without successfully reserving stock.

### Why a separate availability check is insufficient

Suppose two requests read the last tripod before either reserves it:

| Step | Request A | Request B |
| --- | --- | --- |
| 1 | Reads quantity `1` | |
| 2 | | Reads quantity `1` |
| 3 | Decides stock is available | |
| 4 | | Decides stock is available |
| 5 | Records a checkout | |
| 6 | | Records another checkout |

Both reads were valid, but the earlier quantity became stale. A transaction boundary alone does not make a read-then-write decision safe at every isolation level.

The pattern below puts the availability test **inside the update**, then inserts a checkout only from a successfully updated row.

### A. Prepare a repeatable starting point

This reset is only for the synthetic tripod exercise. It deletes the two named demo borrowers' tripod records and restores one unit. It is not a real return-processing workflow. If you added other active tripod checkouts, use a separate fresh practice database before relying on these expected results.

```sql
/* 01 */ BEGIN;
/* 02 */
/* 03 */ DELETE FROM m7_lab.checkout
/* 04 */ WHERE equipment_id = 103
/* 05 */   AND borrower_code IN ('demo-student-a', 'demo-student-b');
/* 06 */
/* 07 */ UPDATE m7_lab.equipment
/* 08 */ SET available_units = 1
/* 09 */ WHERE equipment_id = 103;
/* 10 */
/* 11 */ COMMIT;
```

### B. Make one checkout

**Predict:** How many checkout rows should be inserted? What stock should remain?

```sql
/* 01 */ BEGIN;
/* 02 */
/* 03 */ WITH reserved AS (
/* 04 */     UPDATE m7_lab.equipment
/* 05 */     SET available_units = available_units - 1
/* 06 */     WHERE equipment_id = 103 AND available_units > 0
/* 07 */     RETURNING equipment_id
/* 08 */ )
/* 09 */ INSERT INTO m7_lab.checkout(equipment_id, borrower_code)
/* 10 */ SELECT equipment_id, 'demo-student-a'
/* 11 */ FROM reserved
/* 12 */ RETURNING checkout_id, equipment_id, borrower_code;
/* 13 */
/* 14 */ COMMIT;
```

`WITH reserved AS (...)` names the update's returned result for this statement. The update attempts to claim one available unit. The `INSERT ... SELECT` receives a row only if that claim succeeds.

**Expected:** One checkout for `demo-student-a` and stock reduced to `0`. Do not expect a particular checkout ID: identity values can have gaps, including after rolled-back inserts.

Both changes belong to one statement. If the insert fails, such as because it violates the partial unique index, that statement's inventory change is undone too. The explicit transaction also provides a boundary if additional related work is added later; a failure still requires transaction recovery.

Inspect the results in separate runs:

```sql
/* 01 */ SELECT equipment_id, item_name, available_units
/* 02 */ FROM m7_lab.equipment WHERE equipment_id = 103;
```

```sql
/* 01 */ SELECT checkout_id, equipment_id, borrower_code, returned_at
/* 02 */ FROM m7_lab.checkout
/* 03 */ WHERE equipment_id = 103
/* 04 */ ORDER BY checkout_id;
```

### C. Try a second borrower without resetting

```sql
/* 01 */ BEGIN;
/* 02 */
/* 03 */ WITH reserved AS (
/* 04 */     UPDATE m7_lab.equipment
/* 05 */     SET available_units = available_units - 1
/* 06 */     WHERE equipment_id = 103 AND available_units > 0
/* 07 */     RETURNING equipment_id
/* 08 */ )
/* 09 */ INSERT INTO m7_lab.checkout(equipment_id, borrower_code)
/* 10 */ SELECT equipment_id, 'demo-student-b'
/* 11 */ FROM reserved
/* 12 */ RETURNING checkout_id, equipment_id, borrower_code;
/* 13 */
/* 14 */ COMMIT;
```

**Expected:** No row returned and no new checkout. Stock remains `0`. The application must treat this outcome as an unsuccessful reservation, rather than announcing success just because no SQL error occurred.

In this exercise the reason is exhausted stock. More generally, zero updated rows can also mean the equipment ID does not exist. The operation does not distinguish those cases by itself.

**Explain:** What would go wrong if you inserted a checkout unconditionally after an update that changed zero rows? Why does the unique index alone not prevent two different borrowers from overselling inventory?

## 5. Concurrency, locks, and isolation

**Use case:** Two equipment-desk staff members try to change the same inventory row. A row lock makes an incompatible write wait. For a different task, a report comparing several related totals may need a stable transaction snapshot so its separate queries describe the same view of committed data.

At PostgreSQL's default **Read Committed** isolation level, competing conditional updates to the same row coordinate through row locks. One may wait; after the first commits, the waiting update rechecks its condition against the updated row. If the first used the last unit, the second updates zero rows. If the first rolls back, the unit may still be available.

### Optional two-session lock experiment

Use two independent PostgreSQL connections in DBeaver or `psql`, with explicit control over transactions. Two query tabs sharing one connection are insufficient. With only the Supabase SQL Editor, trace the steps instead.

1. With neither connection holding a transaction, run the reset in Section 4A once.
2. In **connection A**, run the following and leave the transaction open:

```sql
/* 01 */ BEGIN;
/* 02 */
/* 03 */ SELECT equipment_id, available_units
/* 04 */ FROM m7_lab.equipment
/* 05 */ WHERE equipment_id = 103
/* 06 */ FOR UPDATE;
```

`FOR UPDATE` locks the selected row against incompatible writes and locking reads. It does not block ordinary snapshot `SELECT` queries.

3. In **connection B**, run:

```sql
/* 01 */ BEGIN;
/* 02 */ SET LOCAL lock_timeout = '3s';
/* 03 */
/* 04 */ UPDATE m7_lab.equipment
/* 05 */ SET available_units = available_units - 1
/* 06 */ WHERE equipment_id = 103 AND available_units > 0
/* 07 */ RETURNING available_units;
```

**Expected:** B waits, then reports a lock timeout if A still holds the lock. The timeout aborts B's statement and leaves B's transaction failed. Stock is not decremented.

4. In **connection B**, clear the failed transaction:

```sql
/* 01 */ ROLLBACK;
```

5. In **connection A**, release the lock:

```sql
/* 01 */ COMMIT;
```

Always finish both transactions before leaving this exercise. An idle open transaction can keep blocking other work. This example shows **blocking**, not a deadlock: a deadlock requires a cycle of transactions waiting on one another.

### Choose isolation deliberately

| PostgreSQL level | Main behavior |
| --- | --- |
| Read Committed | Default; each statement uses a new snapshot of committed data. A transaction also sees its own earlier changes. |
| Repeatable Read | Uses a stable transaction snapshot; conflicting writes may cause serialization failures. |
| Serializable | Successful transactions have an effect consistent with some serial ordering; applications must handle possible serialization failures. |

PostgreSQL accepts `READ UNCOMMITTED` but treats it like Read Committed. Stronger isolation does not fix incorrect business logic or replace access control.

Run this complete, read-only transaction to inspect the syntax:

```sql
/* 01 */ BEGIN;
/* 02 */ SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
/* 03 */
/* 04 */ SELECT equipment_id, available_units
/* 05 */ FROM m7_lab.equipment
/* 06 */ ORDER BY equipment_id;
/* 07 */
/* 08 */ COMMIT;
```

A serialization failure (`40001`) is different from a successful conditional update that returns zero rows. After a serialization failure, roll back and retry the **entire transaction**, including its reads and decisions, with an appropriate application retry policy. See [PostgreSQL's isolation documentation](https://www.postgresql.org/docs/current/transaction-iso.html).

## 6. Authentication, authorization, and least privilege

**Use case:** A student can view personal loans, desk staff can process returns, and a reporting dashboard can read approved summaries. Each role receives only the operations and data needed for that job.

**Authentication** establishes identity. **Authorization** determines what that identity may do. Signing in does not automatically entitle someone to read every checkout or delete equipment.

The **principle of least privilege** gives each role only the access its work requires. A possible equipment-system design is:

| Operation | Student | Lab staff | Administrator |
| --- | --- | --- | --- |
| View own checkout | Yes | Yes | Yes |
| View all checkouts | No | When required | Yes |
| Create checkout | Through approved workflow | Through approved workflow | Yes |
| Process return | No | Yes | Yes |
| Change table structure | No | No | Yes |

### Inspect your current database context

These queries are read-only. Run them separately:

```sql
/* 01 */ SELECT current_user, session_user;
```

`current_user` is the effective role used for permission checks; `session_user` identifies the session's original authenticated role. They may be the same.

```sql
/* 01 */ SELECT table_schema, table_name, grantee, privilege_type
/* 02 */ FROM information_schema.role_table_grants
/* 03 */ WHERE table_schema = 'm7_lab'
/* 04 */ ORDER BY table_name, grantee, privilege_type;
```

This query shows table grants visible to your current context. Results vary by environment. It is not a complete audit of effective access: inherited roles, schema privileges, ownership, and other access paths matter too.

### Read permission syntax — conceptual only

The following assumes an existing role named `lab_reader`. **Do not run it for this practice**; no permission changes are needed.

```sql
/* 01 */ -- Conceptual permission syntax; not part of the runnable lab.
/* 02 */ GRANT SELECT ON TABLE m7_lab.equipment TO lab_reader;
/* 03 */ REVOKE INSERT, UPDATE, DELETE ON TABLE m7_lab.equipment FROM lab_reader;
```

`GRANT` adds a privilege; `REVOKE` removes the specified grant. Table access also requires appropriate schema access. Revoking a direct grant does not remove privileges available through other roles or `PUBLIC`.

**Explain:** Why should a reporting dashboard usually lack permission to delete inventory?

## 7. Row-level security in Supabase

**Use case:** A student-facing application uses one checkout table for everyone. An ownership policy can restrict each signed-in user's reads to their own rows, while a separately designed staff policy supports legitimate staff access.

Table privileges answer whether a role may perform an operation on a table. **Row-level security (RLS)** can additionally restrict which rows it may access. In a checkout application, Student A might be allowed to see only Student A's checkouts.

The lab's `borrower_code` values are synthetic text labels, not authenticated user identities. They are unsuitable as proof that a request belongs to a particular person.

### Read an RLS policy — conceptual only

This example assumes a **different application table**, `public.checkouts`, with a UUID column named `borrower_user_id`, and Supabase authentication. That table is not created in this lab. **Do not execute this block against the lab or your project.**

```sql
/* 01 */ -- Conceptual example for a separate authenticated application.
/* 02 */ ALTER TABLE public.checkouts ENABLE ROW LEVEL SECURITY;
/* 03 */
/* 04 */ CREATE POLICY "Users can view own checkouts"
/* 05 */ ON public.checkouts
/* 06 */ FOR SELECT
/* 07 */ TO authenticated
/* 08 */ USING (borrower_user_id = (SELECT auth.uid()));
```

Trace the policy:

- `ENABLE ROW LEVEL SECURITY` activates row-level filtering on the table.
- `FOR SELECT` defines a read policy, not permission to insert or update.
- `TO authenticated` targets the authenticated role.
- `USING` tests whether each row belongs to the requesting user.

RLS does not grant missing table privileges. With RLS enabled, ordinary roles require an applicable policy to access rows; owners and roles with bypass privileges can be exceptions. Other applicable policies can also affect access.

The Supabase SQL Editor commonly runs in an elevated context. A successful query there does **not** prove that an ordinary API user is allowed to run it or that RLS is working as intended. A meaningful application test uses the intended client role and user identity, including attempts to access another user's records. See [Supabase's RLS guide](https://supabase.com/docs/guides/database/postgres/row-level-security).

**Check yourself:** If an application receives a permission error, should you disable RLS? No. First identify the request's identity, table privileges, and applicable policies. Keep service-role credentials and database secrets out of frontend code and public repositories.

## 8. Keep user input separate from SQL

**Use case:** A checkout search form accepts a borrower code containing an apostrophe or other punctuation. Parameter binding treats the whole value as data rather than letting its characters alter the SQL structure; authorization separately determines whether the search is permitted.

**SQL injection** occurs when untrusted input is interpreted as SQL code. Building query text by concatenating user input can change the meaning of a query. Parameterized execution supplies the SQL structure and input values separately.

The following is **Python application code**, not SQL Editor code. Read it as a pattern; it assumes an existing Psycopg cursor and connection.

```python
borrower_code = input("Enter borrower code: ")

cursor.execute(
    """
    SELECT checkout_id, equipment_id, borrower_code
    FROM m7_lab.checkout
    WHERE borrower_code = %s
    """,
    (borrower_code,),
)
rows = cursor.fetchall()
```

The SQL string contains a `%s` placeholder, and the value is passed separately as a one-element tuple. Do not substitute it yourself using string concatenation, Python `%` formatting, or an f-string. Placeholder syntax depends on the database driver; this example uses [Psycopg parameter binding](https://www.psycopg.org/psycopg3/docs/basic/params.html).

Parameterization protects the query structure. It does **not** decide whether someone may request that borrower's records. Authorization must still be enforced. Value placeholders also do not substitute table or column names; dynamic identifiers require a suitable composition API and controlled choices.

**Explain:** A user supplies another borrower's valid code to this parameterized query. What separate control must stop unauthorized access?

## 9. Indexes and execution plans

**Use case:** A help-desk screen repeatedly retrieves a small number of events for one equipment ID from a large history table. An index on that ID may reduce scanning. A monthly export that reads nearly every event may benefit much less from that same index.

A correct query can still read more data than necessary. An **index** provides an additional access path, potentially reducing work for suitable filters, joins, or ordering. Indexes also consume storage and add maintenance work to writes.

### A. Generate performance practice data

Run this block once. The event table is independent synthetic performance data, not a checkout history. Its equipment IDs intentionally range from `1` to `100` and do not reference the equipment table.

```sql
/* 01 */ CREATE TABLE IF NOT EXISTS m7_lab.events (
/* 02 */     event_id integer PRIMARY KEY,
/* 03 */     equipment_id integer NOT NULL,
/* 04 */     event_status text NOT NULL,
/* 05 */     created_at timestamptz NOT NULL
/* 06 */ );
/* 07 */
/* 08 */ INSERT INTO m7_lab.events
/* 09 */     (event_id, equipment_id, event_status, created_at)
/* 10 */ SELECT
/* 11 */     g,
/* 12 */     (g % 100) + 1,
/* 13 */     CASE WHEN g % 10 = 0 THEN 'overdue' ELSE 'returned' END,
/* 14 */     timestamptz '2026-01-01 00:00:00+00' + g * interval '1 minute'
/* 15 */ FROM generate_series(1, 20000) AS g
/* 16 */ ON CONFLICT (event_id) DO NOTHING;
/* 17 */
/* 18 */ ANALYZE m7_lab.events;
```

`generate_series` supplies integers from `1` through `20000`. `%` is the remainder operator, distributing records across 100 equipment IDs. Every tenth event is overdue. `ANALYZE` collects statistics for the query planner.

Inspect the data:

```sql
/* 01 */ SELECT
/* 02 */     COUNT(*) AS total_events,
/* 03 */     COUNT(*) FILTER (WHERE equipment_id = 42) AS equipment_42_events,
/* 04 */     COUNT(*) FILTER (WHERE event_status = 'returned') AS returned_events
/* 05 */ FROM m7_lab.events;
```

**Expected in the unmodified practice data:** `20000` total events, `200` for equipment `42`, and `18000` returned events. Rerunning setup skips existing IDs; it does not restore edited rows or remove extra rows.

### B. Capture a baseline plan

On the first pass, do this **before** creating the equipment index in Part C. If you already completed Part C, use a fresh practice database for a clean before/after comparison; an existing index means this is no longer an unindexed baseline.

```sql
/* 01 */ EXPLAIN (ANALYZE, BUFFERS)
/* 02 */ SELECT * FROM m7_lab.events WHERE equipment_id = 42;
```

`EXPLAIN` describes the plan. Adding `ANALYZE` actually executes the query and reports measurements. Here it runs a `SELECT`; on a data-changing statement, `EXPLAIN ANALYZE` would execute that change too.

You will commonly see a sequential scan before the new index. Record your actual output rather than assuming a particular plan or time.

| Plan field | How to read it |
| --- | --- |
| `Seq Scan` | Scans table rows and applies the filter. |
| `Index Scan` | Uses an index to locate matching table rows. |
| `Bitmap Index Scan` / `Bitmap Heap Scan` | Uses an index to identify candidate locations, then visits table pages. |
| `cost=...` | Estimated planner cost, not elapsed milliseconds. |
| Estimated `rows` | Predicted rows emitted by the node. |
| `actual ... rows` | Measured rows emitted per loop; consider `loops` too. |
| `Rows Removed by Filter` | Rows inspected but rejected by a filter. |
| `Buffers` | Buffer activity, such as shared blocks hit in cache or read. |
| `Execution Time` | Measured server execution time for this run. |

### C. Add an index and compare

```sql
/* 01 */ CREATE INDEX IF NOT EXISTS idx_m7_events_equipment
/* 02 */ ON m7_lab.events(equipment_id);
/* 03 */
/* 04 */ ANALYZE m7_lab.events;
```

Now run the same query again:

```sql
/* 01 */ EXPLAIN (ANALYZE, BUFFERS)
/* 02 */ SELECT * FROM m7_lab.events WHERE equipment_id = 42;
```

The filter matches `200 / 20000 = 1%` of the generated rows, so an index-based plan may be useful. PostgreSQL may choose an index scan or bitmap plan. It can still choose a sequential scan when its estimates favor one.

Compare multiple runs under similar conditions. Cache warming, server load, statistics, and measurement overhead affect timing; one faster run does not establish a general speedup. For more plan-reading examples, see [PostgreSQL's EXPLAIN guide](https://www.postgresql.org/docs/current/using-explain.html).

### D. Consider a query that returns most rows

```sql
/* 01 */ EXPLAIN (ANALYZE, BUFFERS)
/* 02 */ SELECT * FROM m7_lab.events WHERE event_status = 'returned';
```

This query returns `90%` of the generated table. The equipment index targets a different column, and even a status index might not help when most rows must be fetched. A sequential scan can be a sensible choice.

**Explain:** Before proposing another index, identify the query's frequency, the fraction of rows it returns, existing indexes, measured plans, and the extra write/storage cost. An index changes physical access; it does not require changing the meaning of the ER model.
